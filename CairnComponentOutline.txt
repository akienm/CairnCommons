1 THE RUNGS (the complexity axis)
  1.1 PURPOSE: Name what every component is, so it has one place to live.
  1.2 INTENTION:
    1.2.1 Tool: a complete primitive. Has users, not an owner. Lives in cairn/tools/.
          Its data for a holder lives under that holder:
          ~/.cairn/devices/<device>/<instance>/tools/<tool>/
    1.2.2 Machine: tools plus the glue that holds them together. Has an owner. Lives
          inside its device (cairn/devices/<device>/machines/<machine>/), or in
          cairn/machines/ if several devices hold one.
    1.2.3 Device: its own process, in the rack, on the bus. See 2.
    1.2.4 Instance: every device has at least one; a singleton is 0.
    1.2.5 First class object (not a device): a thing with a charter that is not a
          rung of its own (Rescue, Graph Trees, Ticket).
    1.2.6 The line between tool and machine is simple vs. complex, and it is
          measured, not judged. A tool calls no other Cairn component (stdlib and
          base only) and owns no state of its own. Anything that calls another
          component, or owns state it must gate, is a machine. A tool that uses
          other tools is a machine. Tools and machines are peers in the tree; the
          rung is complexity, not rank. (Q#1, Akien 2026-11-03: "strict")

2 DEVICE (Implemented as BaseDevice, part of the base tool; a first class object)
  2.1 PURPOSE: A device is a top level cairn entity.
  2.2 INTENTION:
    2.2.1 HARD BOUNDARY: TO ENCAPSULATE EVERYTHING ABOUT A DEVICE IN ITSELF.
    2.2.2 An internal device is its own process. External devices depend on
          implementation.
      2.2.2.1 A device may also own other processes besides its own. They are inside
              the device's boundary. Eg Cairn owns the bus process (where the shims
              run) and the ground loop.
    2.2.3 Devices are all peers with different jobs. See Operator (8).
    2.2.4 A device lives in its own folder in cairn/devices/<device>
    2.2.5 A device's data lives in ~/.cairn/devices/<device>/<instance>/
      2.2.5.1 The instance folder is a number, eg ~/.cairn/devices/cc/0/. A
              singleton is 0.
      2.2.5.2 A device may be a singleton or not, but nothing in its code differs by
              instance.
      2.2.5.3 A bare device name addresses instance 0 (`cc` means `cc 0`); the number
              is written only when it isn't 0. So instance 0 is the default: eg when
              one CC is the orchestrator, it's cc 0 unless directed otherwise.
    2.2.6 A device owns its state: only the device writes under its own
          ~/.cairn/devices/<device>/<instance>/ tree.
    2.2.7 A device holds machines and uses tools (from cairn/tools/). A tool's data
          for that device lives under the device:
          ~/.cairn/devices/<device>/<instance>/tools/<tool>/
    2.2.8 A device talks to other devices only over the bus, never by importing them.
      2.2.8.1 The bus is the only door, with exceptions (Akien 2026-10-22). Each
              is a client tool the device publishes:
        2.2.8.1.1 Database: because faster (13.2.5).
        2.2.8.1.2 Librarian: the embedding links will, I think, work better without
                  device boundaries. Talked about during the first pass at memory;
                  the words came later (4.5.2).
        2.2.8.1.3 Trouble: it has to be able to report when nothing else can, so
                  direct lines to trouble make sense for recovery reasons (7.3.4).
    2.2.9 Every device has the panes defined by base device (19.1.2.5.1): status,
          controls, chat, feed. The web server draws them (18).
  2.3 WHY: Because without hard boundaries Claude creates a tangled mess that exceeds
      Claude's own complexity limit far in advance of completion.
  2.4 COMMANDS:
    2.4.1 get - return a json of some requested thing
    2.4.2 help - the verb list with help strings; always human readable
    2.4.3 list - enumerates verbs, views and panes, any list of things that might be
          published; returns json (show list <foo> formats it for humans)
    2.4.4 put - is given mail or other future push things
    2.4.5 set <setting> <value> - change one of this device's settings (if any); see
          them with list settings
    2.4.6 send <to whom> <what> - this device sends mail to another device, eg
          cairn operator send librarian research <topic>
    2.4.7 show - same as get or list but formatted for humans
    2.4.8 start - start the device
    2.4.9 stop - stop the device
    2.4.10 A machine the device owns that has settings is reached through its device,
           with the same help/list/show/get/set: cairn <device> <machine> <command>
           (eg cairn cairn scheduler list). The bus only ever sees the device, which
           passes the rest down. Machines with no settings (eg base) don't need this.
    2.4.11 Every verb anywhere is reached from the cairn command, as a path:
           cairn <device> [<machine> ...] <verb>. No central list: help at any
           level prints that level's own verbs under [<name>], alpha order, then
           calls back up the tree to its parent, which does the same, out to
           [cairn]. The groups come out flat, one after another, not nested:
               cairn codemother inspector_gadget help  ->
               [inspector_gadget] ... then [codemother] ... then [cairn] ...
           A device may ask another device help over the bus the same way; nothing
           being built needs that yet. (Q#2, Akien 2026-11-03)

3 TICKET (Abstract class - not a device, but a first class object; abstract)
  3.1 PURPOSE: A unit of work or attention, written down so it can be followed.
  3.2 INTENTION:
    3.2.1 TICKET is abstract. Every real ticket is one of the kinds below.
    3.2.2 The abstract ticket owns what every kind shares: its birth (cast) and its
          three parts, each with one job: the plan (only what a builder builds
          from), the metadata and state (what gates and doors read and write as it
          moves), and the history (the append-only log). WHY: one job per part
          reduces confusion; a builder reads the plan and nothing else (Akien,
          2026-10-29 and 2026-11-02).
    3.2.3 The abstract Ticket is either a tool or a machine, never a device; harbor_master
          (10.8) only reports over it. Which of the two is settled by the tool test
          (Law 6): if it must gate writes at its own address, it is a machine.
          (Q#3, Akien 2026-10-28: "it's either a tool or a machine.")
  3.3 KINDS:
    3.3.1 Coding Ticket: what we usually mean.
      3.3.1.1 Has its own workflow stamped on it (the state string, with the cursor).
      3.3.1.2 Each workflow step declares what it needs.
      3.3.1.3 Carries its WATCHME spec.
      3.3.1.4 Lives in CairnCommons/tickets/ while staged; its trail migrates beside
              its code as that component's history while under way, and back to the
              commons after (Law 5).
      3.3.1.5 The ticket owns its refusals: a gate refuses a crossing on the ticket's
              behalf (ruling 2026-08-10). The gates are CodeMother's (10.3.5).
      3.3.1.6 The ticket IS its own manager (Q#32, Akien 2026-11-06). It carries its
              workflow and status, and asks each gate whether it can transit. If
              refused, it gets itself back to design for fixing. If no handler is
              available to ask, it throws a trouble and waits until we decide.
        3.3.1.6.1 WHY: "this format allows every workflow to be different. we add a
                  new kind of thing we do, we build out the handlers for it, and
                  then stamp it's workflow on it, and away it goes, NO OTHER EFFORT
                  FROM US except to set the order things will be built in."
        3.3.1.6.2 Claiming (Akien 2026-11-06): once a gate passes, its post-gate
                  probes alert every available device that can process the next
                  step, and a device comes to claim it. When several compete, the
                  least capable one that thinks it can do it claims it, "leaving
                  the more capable in case a bigger one comes along."
    3.3.2 Inference Ticket: the record of one call to the inference proxy, everything
          that happened to that request.
      3.3.2.1 The call runs the request against our graph trees first. If they can't
              answer, it asks the cloud "what nodes do I need to understand this?",
              integrates them, and runs the query against the trees again.
      3.3.2.2 When it asks an upstream LLM, the nest and its sieves sort out the
              lowest cost way to resolve it (eg by the request's domain), and the
              call is made the way the current constraint set says is best.
      3.3.2.3 Models can be specified, but shouldn't be most of the time. The graph
              trees can be bypassed, but shouldn't be most of the time.
      3.3.2.4 The call returns two pieces: the resolution of the request, and the
              inference ticket.
      3.3.2.5 Used for learning, or for debugging when something fails. A logging
              artifact, so disposable after 30 days.
      3.3.2.6 Inference tickets are transient: they live in the transient tree
              (4.3.2). (Q#4, Akien 2026-10-27)
    3.3.3 Trouble Ticket: an error that needs a non-automated fixer (CC or Akien).
      3.3.3.1 The intention for a trouble ticket is that it is a diagnostic report.
              EXACTLY like the Trouble Tickets in the Number Five Crossbar Telephone
              Switch. It MUST include EVERYTHING needed to diagnose, isolate, and
              repair the trouble.
      3.3.3.2 In the event a second trouble is observed while the first is open, a
              new ticket is NEVER issued, we just increment a counter on the ticket.
        3.3.3.2.1 A trouble has a point of origin, and that is how we match them up.
                  When raised with a condition, its emission source AND error message
                  are checked against open tickets. If found, increment the counter;
                  either way, pass the ticket back to the caller.
        3.3.3.2.2 The incrementing is part of the trouble ticket class.
        3.3.3.2.3 So the error a raiser reports is the same words every time it
                  happens; whatever changes from one time to the next (a pid, a
                  timestamp, a temp path) goes in the details, not the error.
      3.3.3.3 Trouble Tickets are disposable artifacts once closed. They are file
              artifacts, live in the logging tree, and are cleared out on a 30 day
              cycle by the cairn device during a sleep cycle.
      3.3.3.4 If a device experiences an error while servicing a request for another
              device, it can return a pointer to the trouble ticket, and the receiver
              can add new details if they wish.
      3.3.3.5 The test before raising one: can only CC or Akien fix this? If not, it
              is a log line, not a trouble. One problem, one trouble.
      3.3.3.6 They show on the operator's to-do list (8.2.6).
      3.3.3.7 Trouble tickets live inside the recovery device (7.3.4), since
              recovery has to work when other things don't.
      3.3.3.8 A trouble ticket is a work order to fix something. Whoever fixed it
              reports the fix to the originator (the device or machine that raised
              it), and the originator marks it fixed. A trouble that comes back is
              not designed for yet: if we start running into recurrent problems,
              we'll explore that. (Q#5, Akien 2026-10-27; "maybe" on who clears)
    3.3.4 Task Ticket: work the system needs done that does not change code, eg
          deploying our environment onto a second computer to use its compute.
      3.3.4.1 Every ticket has a workflow, even if it is just open/close; that is the
              nature of a ticket (an inference ticket too). A task ticket gets gates
              only if we ever see one closed without actually being done: that is
              what gates are for. (Q#6, Akien 2026-10-27)
    3.3.5 Ideas and questions are not tickets. An idea is a note that leads to an
          intention, and stops mattering once the intention is set down. A question
          exists only to deduce the why: once it is answered, what matters is the
          answer and the why, and nothing else. (Q#7, Akien 2026-10-27)

4 GRAPH TREES MEMORY SERVICE (not a device, but a first class object)
  4.1 PURPOSE: Where Cairn keeps what it knows, and what it holds for a little while.
  4.2 WHY: So everything the system learns is one connected body the librarian can
      see whole, and patterns can be exported from all of it. And so no device
      invents its own way of storing things: there are two ways, and every device
      uses them.
  4.3 INTENTION:
    4.3.1 Knowledge: one list of nodes, owned by the librarian.
      4.3.1.1 Other devices (codemother, chart, ...) keep no node tables of their
              own. They put what they learn into the librarian's nodes through the
              librarian's verbs on the bus.
      4.3.1.2 Each depositor gets its own index over the shared nodes, because each
              asked different questions first while assimilating the data.
      4.3.1.3 The librarian becomes aware of what other parts of the system learned,
              because it is all in its own store, so it can surface what others would
              find useful.
      4.3.1.4 Nodes are kept. The librarian can hand out the next free node.
      4.3.1.5 The shape: one long list of nodes, id = row. Each tree has its own
              table and asks one question. Weights are in the leaves. Links are
              bidirectional. A tree past 5K leaves is calved at its dominant
              attractors, a deterministic code shear. Different trees can index
              the same data in different ways. (Akien 2026-11-03)
      4.3.1.6 The librarian owns every tree and delegates ownership of some to the
              devices that learn: CodeMother, chart, any learning block holds its
              own trees by the librarian's delegation (Law 6: delegation through
              the owner's gate). Why: two holders with different weights over the
              same nodes have different perspectives and can debate points, and
              the librarian, asked anything, can look at the query from both.
              (Akien 2026-11-05)
      4.3.1.7 Delegation nests down the rungs: the librarian delegates a set of
              trees to a device, the device to its machines, a machine to its tools
              if one is ever that complex. Each stays co-owned by the one above.
              CodeMother's learning goes in its own tables, and she owns the
              learning blocks of her machines and tools. (Akien 2026-11-05)
      4.3.1.8 The memory model. Everything Cairn keeps as LEARNING in database
              memory is these five things, and only these. It does not say all
              information lives in trees: logs, troubles, git records and a
              device's own state keep their own homes (4.3.2-4.3.4). One kind of
              access everywhere. (Akien 2026-11-05)
        4.3.1.8.1 Nodes: the one list (4.3.1.5). Every tree indexes it; no tree
                  owns a node, so several trees can index the same node.
          4.3.1.8.1.1 Not every node gets an embedding. Embedding every single thing
                  would make an impossible mound of data, and that is not how
                  Akien works, and this is meant to work the way he does. What gets
                  embedded is the pattern: the answers to a few key questions that
                  cross domains. "How might that work" is chief among them:
                  "it's applicable in almost all domains, and captures the
                  pattern, not the domain specific answer." A node without an
                  embedding is found by its key (eg an exact request). (Akien
                  2026-11-05, open-029c5ae100a9) Which questions those are: 4.3.1.11.
                  (Q#65, Akien 2026-11-05)
        4.3.1.8.2 Trees as tables, permanent: each asks one question, with the
                  weights in its leaves.
        4.3.1.8.3 Trees as tables, temporary: made for one activity and dropped
                  after it. Two kinds named so far: a working tree that sleep
                  builds while consolidating and does not need afterwards, and
                  config read from disk and held in the db. For config the file
                  on disk stays the source: the tree is derived from it, rebuilt
                  when the file changes, never edited in place.
        4.3.1.8.4 Bidirectional links, in lists of their own, id = row. A link
                  that carries a tree's weights lives in that tree's own link
                  list, because the weights belong to the tree's question. A link
                  that is a fact about two nodes (derived from, part of,
                  contradicts) lives in one shared list, readable from either end.
        4.3.1.8.5 Blobs (books, pages, screenshots): a file named by its content
                  hash, plus a node that points at it. A remote box that syncs its
                  db (13.2.6.1) syncs its blobs too.
      4.3.1.9 Lifetimes. Each tree declares its lifetime when it is made: kept, one
              activity (eg one sleep run), or until its source file changes.
              Dropping a tree drops its leaves and its own links. A node goes only
              when no tree indexes it, so whatever a temporary tree's activity
              promoted into a permanent tree outlives it. The drop is enforced, not
              a habit: measured 2026-11-05, 61 test tables sit in the db, left by
              runs that ended without dropping them.
      4.3.1.10 NOT HOW IT IS NOW (measured 2026-11-05; Akien: "I believe that it's
              not how it is now"): a node's id is a hash of its content
              (node_id_for, trees.py:126), not its row; the shared link list
              cairn_links has 0 rows; there are no per-tree link lists, no blob
              store, and no lifetime on any tree. Every node is embedded: the
              deposit door refuses a node without a vector (trees.py:250), and
              cairn_embeddings holds 21,880 embeddings for 21,082 nodes (798 point
              at no node). Walks derive their edges from vector proximity (nearest,
              neighbors); the stored-link door (trees.link) has written none.
      4.3.1.11 Cross-domain questions: a special kind of question, inherently
               cross domain (or cognition questions), not domain specific. "How
               might that work?" is Akien's number one. They are not design
               questions: a design question is a spec choice waiting on Akien
               (cairn question, CairnCommons/questions/). (Akien 2026-11-05)
        4.3.1.11.1 A question is a node in the one list (4.3.1.8.1). Questions can
                   belong to devices, and two devices can have the same question:
                   both hold the same node. A device that owns a question is a
                   delegate, because all knowledge belongs ultimately to the
                   librarian (4.3.1.6). Owning a question = holding a tree for it,
                   with that device's own weights.
        4.3.1.11.2 The answers to cross-domain questions are what get embedded
                   (4.3.1.8.1.1): an answer from any domain lands in that
                   question's tree as a pattern, so a later search under the same
                   question finds patterns from other domains ("which often
                   initiates a cross domain search", Akien 2026-07-14).
        4.3.1.11.3 The corpus is a git JSON file beside the librarian's code
                   (shareable spec, 4.3.4); the question trees are derived from
                   it. Every entry carries its origin: verbatim (Akien's words,
                   with date and source) or proposed (by CC, by Gemini, ...). All
                   questions are included; the origin keeps his words apart.
                   (Akien 2026-11-05: "we can include all the questions. i expect
                   i have a couple of hundred in my own head.")
        4.3.1.11.4 Questions that fire in sequence are linked "followed by" in
                   the shared link list (4.3.1.8.4), so a walk can run a
                   sequence. Two known: mechanism, need, fit, get inside,
                   experiment (Novelty.txt 2026-07-14); best pattern, gaps, trim
                   to fit, how might that work (cortical columns, 2026-07-02).
        4.3.1.11.5 Harvest: a deterministic pass over Akien's logs and notes
                   proposes question-shaped lines in his words; he confirms each
                   before it is marked verbatim. New ones are added through a
                   librarian command as he says them.
        4.3.1.11.6 NOT HOW IT IS NOW (measured 2026-11-05): the corpus lives in
                   CodeMother (cairn/devices/codemother/cognition_questions.json,
                   embedded by seed_trees.py) with 13 of UU's 18 verbatim
                   questions (Q-cog-014..018 lost in the move), Akien's 3 from
                   Novelty.txt, and 11 Gemini-worded questions labelled "Akien
                   verbatim".
    4.3.2 Transient: the transient tree (what the logging tree becomes).
      4.3.2.1 Everything held for seconds to days lives here: mail, logs, test runs,
              trouble tickets, inference tickets.
      4.3.2.2 Each kind of thing declares its lifetime, and it ages out on that clock.
      4.3.2.3 Cairn owns all of ~/.cairn/ and delegates each ~/.cairn/devices/
              subtree to its device. Everything outside devices/ (~/.cairn/logging/
              and the rest) is Cairn's, so every log is Cairn's and Cairn cleans
              them up in sleep. Transient things are files there. Trouble tickets
              are logging items.
      4.3.2.4 The transient tree is for things that may help debugging out to 30
              days and won't be needed past that, eg an inference ticket looked at a
              week later because a bug turned up. No trouble should stand unresolved
              at 30 days; sleep's cleanup may be made to spare one that does.
              (Q#8, Akien 2026-11-03)
    4.3.3 A device's own state lives in its ~/.cairn/devices/<device>/<instance>/
          tree.
    4.3.4 Shareable provenance (charters, tickets, validations) is git JSON beside
          the code, never a row.
  4.4 ANTI-INTENTION:
    4.4.1 Each device growing its own pool of tables (today: 16 node tables, several
          owners).
    4.4.2 Any device reaching into the librarian's code other than through the trees
          tool it publishes. (Measured 2026-11-05: chart reaches its own trees
          through that published tool, cairn.devices.librarian.tools.trees.trees,
          imported at cairn/tools/tree/tree.py:58. That is the delegation of
          4.3.1.6, not a breach; "today chart does" was a misunderstanding.
          Akien 2026-11-05)
  4.5 COMMANDS:
    4.5.1 The librarian's verbs for depositing and walking. See 9.4.
    4.5.2 Walks go through the librarian's published trees tool, not the bus
          (2.2.8.1.2).
    4.5.3 Most devices submit queries to the trees and never walk them: walk,
          nearest and neighbors are encapsulated by the librarian, which owns the
          processes of memory the way CodeMother owns the code and sees to its
          well-being (10.1). They can be made available through a tree class and
          bus verbs, but using memory happens at a higher level than that for
          most devices. (Q#29, Akien 2026-11-05: "that's why we have the
          librarian at all, to encapsulate and own those processes")

5 CAIRN DEVICE (cairn/devices/cairn/)
  5.1 PURPOSE: Represents the cairn system in aggregate
    5.1.1 Cairn owns everything about the system that is Cairn and hasn't been
          delegated elsewhere. A delegated domain belongs to its device, not to
          Cairn, even though it is of Cairn: eg the librarian is delegated learning,
          research and answering queries on what's learned; the embeddings device is
          delegated producing the embeddings we search with. The OS and hardware
          belong to Recovery (7.6).
    5.1.2 The embeddings device is real and comes first: the first device after CC
          and Cairn, before the librarian, because the librarian will be its biggest
          user. See 16. (Q#9, Akien 2026-11-03)
  5.2 INTENTION:
    5.2.1 Drive sleep process for devices
      5.2.1.1 Cairn keeps a list of scheduled things (the scheduler, 5.8). Each
              ground loop pulse, its shim has Cairn check that list against the
              clock: no match (eg 2245), the pulse is dropped; a match (eg 2300) is a
              PROBE, and it kicks off that thing in the Cairn device.
      5.2.1.2 Sleep is one of those scheduled things. At its time Cairn kicks off
              sleep by running its own sleep routine, then hands the sleep token over
              the bus to the next device, and so on. The rack's order is the token's
              order (5.6.2.3).
      5.2.1.3 What each device does in its sleep depends on the device: the librarian
              consolidates memory; the learning blocks do the same on their smaller
              memory sets; Recovery might run backups or SSD checks; some (eg the word
              graph embeddings device) do nothing.
      5.2.1.4 Cairn's own sleep has a lot to do, including clearing the logging tree
              of things older than 30 days.
      5.2.1.5 Sleep's base trigger is the clock (2300). Once we can tell how
              recently things were interacted with, that overrides the base clock.
              (Q#10, Akien 2026-11-03)
      5.2.1.6 When this box may be used is decided from three inputs. The
              schedule sets a baseline. Observing Akien (how recently things were
              interacted with) can open time that would otherwise not exist:
              measuring trumps rules. An away window ("going to bed", "out to the
              theater", x to y) does the same.
        5.2.1.6.1 An opening lets the system as a whole put every available
                  resource on a task or group of tasks. No orchestrator: no box
                  hands work to another. Work shows up in the harbor (tasks,
                  tickets, whatever), and any box with an opening runs it. Little
                  use today; it matters once a lot is going on. (Q#11, Akien
                  2026-11-03)
        5.2.1.6.2 Example (the Igor stage): populating the word graph for the
                  embeddings generator, all 4 laptops read one block at a time
                  into the database, with local inference in ollama on 10th-gen
                  i7Us, no GPUs, very long timeouts. It worked because a block
                  could take 5 minutes.
    5.2.2 Own foundational components (bus, ground loop, rack, shims, scheduler,
          launcher). The scheduler is the base shim's (5.8); harbor_master is
          CodeMother's (10.8).
    5.2.3 Owns the cairn command line launcher (5.3).
    5.2.4 Owns the transient tree and its 30 day sweep (4.3.2.3).
    5.2.5 `cairn start` (= cairn cairn start) brings the system up: ground loop, bus,
          shims. `cairn stop` takes it down.
      5.2.5.1 Any cairn command brings up whatever it needs, including the whole
              install on the very first run (7.3.2). A well designed tool should
              disappear in use.
    5.2.6 There is no central supervisor. Each part starts what it needs by trying
          to use it: sending a message starts the bus if it is down, a message
          arriving wakes its shim, the shim wakes its device. Many very small
          supervisors, each one detect-and-start. (Akien 2026-11-04)
      5.2.6.1 The detect-and-start lives in one tool, the waker (CC's name), and it
              sits inside connect: every client's connect is a wake attempt, so no
              caller can forget one. A probe watches and reports; the waker acts.
      5.2.6.2 Two callers waking the same part at once start only one: the part
              that binds its socket first is the only one; a second copy finds it
              taken and exits quietly (as the ground loop does, 5.5.3.3).
      5.2.6.3 What the waker starts outlives whoever started it (detached, or
              through systemd-run --user, which gives it its own memory cap and log
              while still deciding nothing). Restarting a shim never takes down the
              bus it once woke.
      5.2.6.4 A wake waits until the part answers, at most 60 s (5.4.2.9). Repeated
              failures back off, then file a trouble (5.7.3.2.2), so a crash loop
              cannot spin.
      5.2.6.5 Nobody sends to the ground loop, so the cairn command (and login) wake
              it; its pulse then wakes the shims (5.7.3.4).
  5.3 launcher (machine)
    5.3.1 PURPOSE: The operator's ramp onto the bus.
    5.3.2 INTENTION:
      5.3.2.1 The launcher is a machine owned by the Cairn device. It is mostly a
              router.
      5.3.2.2 The launcher walks the words. `cairn cairn foo bar` (the long form)
              means "tell the cairn device to run foo with argument bar". At each
              level: is the next word a machine here? Step into it and take the
              next word. Is it a script in this level's bin/? Run it, pass back the
              result, done. Neither? It is a bus verb: send it to this level over
              the bus. So `cairn foo bar baz`: foo is a device; it has a machine
              bar; bar's bin/ has baz, so baz runs. No bar machine? bar goes to
              foo over the bus. Each check is one directory lookup, so it is fast.
              (Q#12, Akien 2026-11-03)
      5.3.2.3 Any device or machine may have a bin/ beside its code
              (cairn/devices/<device>/bin/, .../machines/<machine>/bin/). That
              folder IS its list of shortcuts: add a file to add one, delete it to
              remove one. A shortcut is just a script that calls the long form,
              which also saves the walk from searching farther (eg `cairn
              superclaude` → `cairn cc superclaude`; `cairn show temp` → `cairn
              recovery show temp`), or does work itself (eg initialization,
              install). Shortcuts can go anywhere, beside what they serve (RULE 1).
      5.3.2.3.1 `cairn foo` whose first word is not a device means `cairn cairn
              foo`: top-level shortcuts are the cairn device's bin/.
      5.3.2.4 Scripts are Python wherever possible, run by Cairn's own interpreter,
              so one file works on every platform. Platform-specific ones match their
              platform: executable or .sh on Linux; .bat, .cmd or .ps1 on Windows.
      5.3.2.5 If a shortcut has the same name as a device, the launcher warns "x
              hides y" and then runs x.
      5.3.2.6 `cairn` speaks as the Operator (8).
      5.3.2.7 If Cairn isn't set up, or won't come up, the launcher calls the
              recovery device directly, not over the bus (7.3.1).
    5.3.3 HISTORY: today it is bin/cairn dispatching to bin/cmd/<name>, 31 commands,
          most of which do the work themselves. Where each goes: 5.10.
    5.3.4 Repo-root bin/ holds only the launcher itself (cairn, cairn.cmd), the one
          thing on PATH, so it runs even when the package won't import (5.3.2.7).
          Every shortcut lives in the bin/ of the device or machine it belongs
          to. Its bin/ plus its bus verbs is what help lists at that level
          (2.4.11). (Q#12: Akien let CC choose, 2026-11-03; CC kept his walk.)
  5.4 bus (machine)
    5.4.1 PURPOSE: To provide an inspectable message passing system.
    5.4.2 INTENTION:
      5.4.2.1 It is the only way devices talk to one another.
      5.4.2.2 Every part is its own process: the bus, each shim, each device, the
              ground loop. Any one of them can be stopped and restarted alone while
              the rest run on, which a self-modifying system needs. (Akien
              2026-11-04)
      5.4.2.3 The bus handles two kinds of requests:
        5.4.2.3.1 Send - Asynchronous. Like sending an email.
        5.4.2.3.2 Show/Get - Synchronous. Like requesting a web page.
      5.4.2.4 The messages are stored in a SMALL buffer in memory, because in memory
              is faster.
        5.4.2.4.1 A message nobody picks up within n milliseconds is pushed out of the
                  buffer to the database, into a table that is just a table of
                  messages. That table is the bus's exception to the memory model
                  (4.3.1.8): it is not learning, and the buffer in front of it is
                  what keeps the bus fast. (Akien 2026-11-05, from a UU-days
                  discussion.) Today bus_traffic holds every message (59,883 rows,
                  measured 2026-11-05).
        5.4.2.4.2 [Q#64: does 5.4.2.4.1 replace "a shim that needs to hold mail puts
                  it in the transient tree", or do both stand?]
      5.4.2.5 The shims, each connected to the bus, pick up the messages and route
              them to their device in whatever manner is appropriate.
      5.4.2.6 The Operator Device and the 'cairn' command are the operator's route
              onto the bus.
      5.4.2.7 The bus makes this messaging inspectable, the messages show on the
              bus' web panel as a "Murderbot Diaries" "Public Feed" the operator can
              review for purposes such as diagnostics.
        5.4.2.7.1 The feed is for debugging: "did the thing go by when I typed the
                  command?"
        5.4.2.7.2 It holds about the last 5 minutes, in the bus's memory buffer, and
                  is empty after a bus restart. The Cairn device owns it, since the
                  bus is its machine.
        5.4.2.7.3 The panel is drawn by the public_feed tool (19.3).
        5.4.2.7.4 Each line: from, to, time, sync/async, message.
      5.4.2.8 One bus per cairn instance (not per host). The bus owns cross system
              communication: extending the bus services to other host systems so
              we can run multiple heavy tasks at once.
        5.4.2.8.1 Each box runs its own bus, and the buses talk to one another, so
                  a device always talks to the bus on its own box. Together they
                  are the instance's one bus. (Akien 2026-10-28)
        5.4.2.8.2 A device runs on one box; the other boxes reach it over the
                  buses. No box needs a full set of devices. (Akien 2026-11-04)
      5.4.2.9 A shim waking its device should never take more than 60 s. A sync
              caller waits at most 60 s for the wake, then gets "not now" back; a
              wake that misses 60 s is a trouble. 600 s is the limit for an
              inference call to come back, not for a wake. (Q#13, Akien 2026-11-03)
      5.4.2.10 A message is addressed to a name (a device instance), never to a
              connection. A shim that restarts reconnects and answers to the same
              name, so restarting it never restarts the bus. (Akien 2026-11-04)
      5.4.2.11 The bus is as fast as we can make it. Which way it carries messages
              (a plain Unix socket, NATS, or Postgres NOTIFY) is settled by
              measuring each on this box, not by choosing. Large things (embeddings,
              documents) never ride the bus: they go to the database or a file and
              the message carries the id. Database access stays an import in each
              process, one connection each. (Akien 2026-11-04)
        5.4.2.11.1 Measured 2026-11-04 on this box, a 536-byte message, request
                  and reply, every side its own Python process, p50 over 5,000
                  (two runs each): our own small broker on Unix sockets, routing
                  by name, 50 µs; Postgres NOTIFY 110 µs; NATS request/reply 250
                  µs (its Python client is the slow part); NATS durable publish
                  150 µs. A direct socket with no broker is 10 µs. So the bus is
                  our own broker on Unix sockets: the fastest, and it already
                  fits 5.4.2.4 (no database, a small buffer), which was the one
                  thing NATS offered beyond speed. (CC, measurement; the bench is
                  scratch, not yet a tool)
        5.4.2.11.2 Waking costs 15 ms for a bare Python part and 65-90 ms for
                  one that imports like a shim (setsid; systemd-run adds about 20
                  ms). That is far inside the 60 s of 5.4.2.9. (CC, measurement)
        5.4.2.11.3 A Unix socket path cannot be longer than 108 bytes, so a
                  socket address is kept short and never nests deep in a device
                  tree. (CC, found while measuring)
        5.4.2.11.4 Unix sockets carry the bus inside a Linux box. Between boxes,
                  and on Windows, it is TCP: Python on Windows has no AF_UNIX
                  (measured 2026-11-04, akiendell: the web server died on
                  `socket.AF_UNIX`), and buses on two boxes (5.4.2.8.1) can only
                  reach each other over the network. (Akien 2026-11-04, "yes
                  please")
        5.4.2.11.5 Box to box, the bus speaks TLS with pinned certificate
                  fingerprints checked both ways; cairn install makes each box's
                  certificate. No tunnel, nothing extra to run. (Akien 2026-11-04:
                  "TLS sounds like the win to me, more in line with 'no extra
                  things to set up'"; replaces ssh tunnelling, open-06cfefbe745e)
    5.4.3 HISTORY: the bus once wrote its ring to the database on each pulse
          (2026-09-06). V1's "keeps no database" replaces that.
    5.4.4 TOOLS: base, public_feed
    5.4.5 VERBS: None
  5.5 ground_loop (machine): the heartbeat
    5.5.1 PURPOSE: Cairn system daemon
    5.5.2 ANTI-INTENTION:
      5.5.2.1 What it must never grow back: a bus, a shim, probes, other kinds of
              pulses, staleness
    5.5.3 INTENTION:
      5.5.3.1 It is the only daemon in the system
        5.5.3.1.1 "Only daemon" means the only thing that wakes on a clock. The
                  system is event driven, and the ground loop provides the timed
                  checking such a system needs. Most things need no timing; the
                  few that do hang off the ground loop, directly or indirectly (eg
                  through the scheduler, 5.2.1.1), never on a daemon of their own.
                  Why: CC once made a daemon for everything. (Q#14, Akien
                  2026-11-03)
      5.5.3.2 It re-starts itself when its own files change, unless
              COMMAND_DO_NOT_RESTART is set. COMMAND_EXIT stops it with exit code 0.
      5.5.3.3 A second copy refuses to start.
      5.5.3.4 it launches a script in each device's cairn/devices/<device>/groundloop
              called pulse.py, each as its own process.
      5.5.3.5 It writes one JSON record at the end of a pass with a list of each
              device: beat time, found device (folder), NOT FOUND or name, file
              mtime, pid it spawned. It does no checks and no takeover.
      5.5.3.6 Beat interval is a setting, 60 s for now. It was held at 60 s while
              too much hung off the ground loop; that is cleaned up, and we expect
              to go a lot faster later (Akien: "faster than once a second"). (Q#15,
              Akien 2026-11-03)
        5.5.3.6.1 So the scheduler (5.2.1.1) fires an entry whose time fell since
                  the last beat, not one that equals the beat's minute: then any
                  beat length fires each entry exactly once. (CC, following from
                  Q#15)
    5.5.4 HISTORY: I once made daemons for everything and couldn't shut them down. So
          there is one loop, kept as simple as possible. In your words: "this is
          ENTIERLY an event driven system EXCEPT: Akien can say he'll be away from x
          to y times. and sleep."
    5.5.5 TOOLS: base
    5.5.6 VERBS: None
  5.6 rack (machine)
    5.6.1 PURPOSE: The place that holds the devices: a stack of rackmount devices,
          with the bus connecting them all.
    5.6.2 INTENTION: Just a dict with the device instances in it, in the form of
          their shims.
      5.6.2.1 It holds instances, not classes: one shim per instance. If we have cc 0
              and cc 1, two shims are running.
      5.6.2.2 It is the shims connected to the bus: who's in the rack is who's
              connected, which the bus can measure (agreed 2026-10-26, since each
              shim is its own process, 5.7.3.1).
        5.6.2.2.1 A shim that isn't running isn't connected, so it isn't in the
                  rack. The rack says what is running; it is not where instances
                  are declared (5.6.2.4). (Q#16, Akien 2026-11-04)
      5.6.2.3 The sleep token goes round in sequence, one sleeper at a time, so that
              no one sleeper takes the whole system to everyone else's cost. The
              order itself doesn't matter: it is alphabetical by device, then by
              instance. That is the same on every box and needs nothing stored.
              (Q#17, Akien 2026-11-04; alphabetical is CC's pick)
      5.6.2.4 An instance is declared by its folder existing in class-space:
              cairn/devices/<device>/<instance>/ (one address in two roots). Declared
              = the folders; running = which of those are in the rack. (Q#18, Akien
              2026-11-04)
    5.6.3 HISTORY: today there is also a rack TOOL (19.20) that lists device folders.
          The machine holds running instances; the folder list may stay a tool.
  5.7 shims
    5.7.1 PURPOSE: Integrates its device into the system.
    5.7.2 WHY: So any program, ours or not, can live in Cairn as a device.
    5.7.3 INTENTION:
      5.7.3.1 Every device has a shim. Each shim is its own process, one per
              instance, and connects to the bus as a client (agreed 2026-10-26).
        5.7.3.1.1 WHY: in the bus process, updating one shim meant bringing the
                  whole bus down, and one shim's stall (or lock) was everyone's
                  (bug c2036433beaf: two shims' locks deadlocked in the bus).
                  Separate, a shim restarts itself when its own files change, like
                  the ground loop (5.5.3.2), and the bus stays up.
      5.7.3.2 The shim always starts its device. Nothing else does.
        5.7.3.2.1 It wakes the device when it's not running and is needed.
        5.7.3.2.2 If the device won't come up, the shim retries; after many retries
                  it files a trouble ticket for Akien and CC to check. This holds for
                  every wake: a request, a pulse, the sleep token (eg the web server
                  failing to come up).
        5.7.3.2.3 It answers what it can itself; when it can't (eg a health question
                  it holds no answer to), it wakes the device and asks.
        5.7.3.2.4 A device may declare an idle time; the shim stops it after that
                  long unused, and the next message wakes it again (5.2.6). With
                  none declared it runs until `stop`. Idle costs memory, not CPU,
                  so eg the librarian, slow to load, stays warm for hours, while
                  something cheap can stop after a minute. (Q#19, Akien 2026-11-04)
      5.7.3.3 Processes all messages from the bus for its device.
      5.7.3.4 pulse.py is part of the shim. The ground loop calling it tells the shim
              the pulse has arrived, and starts the shim if it isn't running.
        5.7.3.4.1 The ground loop finds one pulse.py per device. pulse.py reads its
                  own device's declared instances (5.6.2.4) and pulses each one, so
                  the ground loop never needs to know instances exist. Pulsing an
                  instance that isn't connected is what starts its shim; once
                  connected, it is in the rack. (Q#16, Akien 2026-11-04)
        5.7.3.4.2 Any device's shim (through its pulse.py) can bring the bus up if
                  it's down: whatever is called brings up what it needs (5.2.5.1).
        5.7.3.4.3 pulse.py asks nobody anything. It starts the shim if it's down,
                  else tells the mechanisms inside the shim that need a pulse "here
                  ya go!" Only daemon-shaped things hang there, things that actually
                  need a heartbeat; everything else fires on events. Eg cc's Gmail
                  fetch, which IS messaging (12.3.6).
          5.7.3.4.3.1 WHY (Akien, 2026-10-26): "you were shoving more and more
                      things into the ground loop. making it slower and slower. the
                      point behind the ground loop firing pulse.py was to give you a
                      structure to hang deamons from, not managers."
      5.7.3.5 Processes the sleep cycle, if its device needs one: when the sleep token
              arrives, it wakes its device to do its sleep (the device does the
              sleeping, not the shim), then passes the token on. If its device won't
              come up, the shim files the trouble and still passes the token on, so
              the rest of the rack sleeps.
      5.7.3.6 Writes its runtime data, if any, to ~/.cairn/devices/<device>/<instance>/
      5.7.3.7 Three kinds of device sit behind a shim:
        5.7.3.7.1 Internal (eg librarian): ours, engineered to work with its shim, so
                  the shim adapts little.
        5.7.3.7.2 External (eg Claude Code): a program we don't control; the shim does
                  the adapting that lets it exist here.
        5.7.3.7.3 Virtual: the shim is the whole device. Eg a calibre device that
                  talks to calibre's own database, or a weather device over the
                  acurite data, for when something else in Cairn (say, a personal
                  assistant scheduling outdoor events) wants the weather.
      5.7.3.8 The shims handle all interfacing with the outside world (ruling
              2026-09-11): a device that needs to speak a foreign protocol (eg
              OpenAI's wire format) does it in its shim.
    5.7.4 COMMANDS: The Device commands. The shim answers start and stop itself.
  5.8 scheduler (part of the base shim, 5.7; was sleep_cycle): uses tools base, rack
    5.8.1 PURPOSE: Holds each device's list of scheduled things.
    5.8.2 INTENTION:
      5.8.2.1 The pulse triggers the check: each pulse, the shim checks its device's

7 RECOVERY DEVICE (cairn/devices/recovery/; Recovery And Installation Manager;
  holds the host (was the System device), install, upgrades, root, Rescue and
  trouble tickets)
  7.1 PURPOSE: Owns the host Cairn runs on. Gets Cairn installed and running, gets
      it running again when it breaks, and reports usefully when things don't work.
  7.2 WHY:
    7.2.1 A well designed tool should disappear in use: so little friction it's
          almost an extension of the user. Traditional software makes installing,
          opening and using it three separate tasks; Cairn makes them one command.
    7.2.2 It's part of our recovery system, so it has to work when other things
          don't, so I can report usefully on them.
  7.3 INTENTION:
    7.3.1 It operates when the bus is down, and when nothing is installed at all.
          The cairn command calls it directly.
    7.3.2 The very first run:
      7.3.2.1 A user downloads Cairn for the very first time. The readme says
              `cairn/bin/cairn librarian` (the full path, because no paths to the
              cairn command are set up). No database is installed. Nothing.
      7.3.2.2 The cairn command sees that, and calls the recovery device directly,
              reporting that we're not set up.
      7.3.2.3 It explains to the user that before we can start the librarian we need
              to do a few things first. Easy setup or DIY setup? Most people will
              take the easy setup.
      7.3.2.4 It asks for your password so it can install a, b, c, d. The password
              is kept only in an env var, and goes away when the program ends.
      7.3.2.5 If we can sort our location, we don't ask the user. If Cairn needs a
              password of its own (highly likely at some point), it asks during this
              setup.
      7.3.2.6 We install and set up everything, and the user is presented with a web
              based chat window (the librarian's).
      7.3.2.7 So the user entered a single command, and all needed setup was complete
              with an absolute minimum of interaction.
    7.3.3 Later the user changes something and breaks it. Recovery is called again,
          and invokes Claude (Rescue, 7.5) if needed to get it all fixed up.
    7.3.4 Trouble tickets (3.3.3) live here. Any device has a direct line to raise
          one, not over the bus (2.2.8.1.3).
    7.3.5 Install and upgrades live here. If xyz library needs an update, this is
          the component that does it. Any change to what the host is goes through
          here (7.6.2.1.1). The installer machine (today cairn/machines/installer)
          walks the host-seam intentions, verifies each, offers what's missing,
          applies, re-verifies.
    7.3.6 It has a shim, like every device, so it's on the bus when the bus is up
          (upgrades, its troubles, its last repair). It's still called directly
          when the bus is down or Cairn isn't installed (7.3.1).
    7.3.7 The setup panels (easy and DIY alike):
      7.3.7.1 Each panel is a block of text asking a question, with the default
              answer selected, so the user can go next, next, next until they reach
              the thing they want to change.
      7.3.7.2 A panel isn't one question each: a set of simple, related questions
              (eg 10) goes on one panel, to approve all or adjust before next.
      7.3.7.3 Or a statement: "the following necessary things will be installed:"
              and the list, with the why for each one.
      7.3.7.4 One setup question: "Is this a cairn home? No? Then what's the
              hostname/IP for the cairn home I should attach to?" The answer is an
              env var (CAIRN_HOME_HOST), beside the ones for where the repo and the
              runtime folder are. akiendelllinux is the cairn home for this install;
              akiendell attaches to it. (Akien 2026-11-04)
    7.3.9 sudo_relay (machine; today its own device, cairn/devices/sudo_relay):
          Recovery's way to root on Linux, needed for installs and upgrades.
      7.3.9.1 A command goes in, runs as root, and a permanent audit record comes
              out: the command line, return code, stdout, stderr, plus an id and
              date. The audit folder keeps a rolling one month.
      7.3.9.2 A machine, not a tool: it keeps the audit records (state it must gate),
              and runs as its own root process inside Recovery's boundary (2.2.2.1).
      7.3.9.3 Other platforms get their own way to root (eg on Windows, Rescue and
              the installer run from an elevated PowerShell, 7.5.3.3).
      7.3.9.4 Any device may ask Recovery to run something as root. The operator
              answers each ask: decline, accept now, accept always, accept with a
              new rule, or (for a chat-enabled device) chat about it. Cairn owns
              it. (Q#23, Akien 2026-11-04: "i would say any device should be able
              to ask, and the operator can decline, accept now, accept always(,
              accept with new rule - how we express that to be defined later),
              chat about this (for chat enabled device) and cairn owns")
        7.3.9.4.1 A new rule, for "accept with new rule": in the moment, an LLM call
                  helps ask the question and sorts the answer, so the rule can be
                  cast. CC's call: the cast rule is DATA (which device, the command's
                  argv prefix or pattern, an optional expiry), checked by plain code;
                  never code run through eval(), because the rule guards root and a
                  rule that runs code is itself a way to root. (Q#63, Akien
                  2026-11-04: "a new rule ... could be a piece of code suitable for
                  an eval() call. or it could be an llm call in the moment to help ask
                  the question and sort the answer so code can be cast. you can make
                  the call about one of those or something else.")
  7.4 COMMANDS:

  7.5 Rescue (Claude Code outside Cairn; part of recovery, not a device of its own)
    7.5.1 PURPOSE: The mechanic. Claude Code running outside the system, called when

          pieces or get us set up."
    7.5.2 WHY: A broken system can't fix itself, and a deterministic installer can't
          handle what it didn't foresee. CC is a senior builder INSIDE Cairn; Rescue
          is Claude outside it, getting it running and keeping it running.
    7.5.3 INTENTION:
      7.5.3.1 Each platform gets a good deterministic installer. When it fails, it
              falls over to Rescue.
      7.5.3.2 When something won't start (eg the database), Rescue is who gets
              called.
      7.5.3.3 Bringing Cairn to a new platform is a Rescue job, done on that platform
              (eg Windows, built from inside an elevated PowerShell, because Claude
              writes better Windows code on Windows).
      7.5.3.4 Needs nothing of Cairn's to run: no bus, no tmux.
      7.5.3.5 Launched automatically by a failed install or start, with "read this"
              and a file saying what happened and what it wants to make happen. The
              operator can also launch it by hand.
      7.5.3.6 Always launched with dangerous permissions, so it CAN do what's needed.
      7.5.3.7 What Rescue fixes by hand, it turns into a step in that platform's
              deterministic installer, so next time the installer handles it alone.
              Each rescue makes the next one less likely: the system keeps learning.
      7.5.3.8 On a new platform (eg Windows) a simple cairn.bat comes first: at the
              start it takes only the rescueclaude option, launching Claude with 200K
              context and dangerous permissions.
      7.5.3.9 Code home: launchers/ (bootstrap.sh, the python floor that comes up
              before anything else) moves into the Recovery device, and
              superclaude (the CC launcher, 12) moves to the CC device. (Q#24,
              Akien 2026-11-04: "yes to both")

      7.5.4.1 cairn rescueclaude - launch Rescue's Claude Code. It starts nothing
              else. (Contrast cairn superclaude, which brings the rest of Cairn up

    7.6.1 PURPOSE: Abstracts the swarm of systems that Cairn is running on.
    7.6.2 INTENTION:

              Cairn itself belongs to the Cairn device or to whichever device it's

        7.6.2.1.1 The line is using vs changing. Any device may USE the OS's

    19.14.1 ROOT INTENTION for checks and gates (Akien, 2026-10-27): the inspector
            does all the checks, so there is no need for more checks anywhere else.
            The inspector's output is consumed by the gate. The gate's output is the
            certificate. "This was how I meant it all along."
    19.14.2 The certificate is one file type you can't write. It carries a
            cryptographic (or similar) way to say that the right code wrote it, on
            this date, at this time, with these hashed findings.
    19.14.3 That signing belongs in the base gate class, so every gate has it.
    19.14.4 Entry gates exist only to kick back what doesn't meet the entry
            requirements. Nothing in them is about who writes what.
    19.14.5 The crossing is the ticket's own act. The gate's probe (the same kind
            that sends notice of gate passage) tells the passing ticket "you can
            now advance to X", and the ticket updates itself. (Q#61, Akien
            2026-10-27)
    19.14.6 What a gate asks is "does this meet the intentions", never who did it.
            Every intention carries a why, and so does every test case whose purpose
            is not plain. A change that makes a ticket or a test case meet the
            intentions better is good, and downstream supports it when the whys show
            it isn't a fast one. Measuring who did what serves none of that
            (Akien, 2026-10-31).
    19.14.7 The inspectors are not assumed correct; they are examined when they
            refuse. A failure is not automatically "it broke, change it". After a
            gate refuses, an LLM sets the refusing sieve's intention and why
            beside the ticket's intention and why and asks: is this sieve the best
            we can do right now? If yes, the ticket changes. If no, the sieve is
            fixed. Either way the system improves, constantly. WHY: questions about
            a part are answered by its intention and why against the new thing's
            intention and why, so a disagreement becomes an update to an intention
            or to its implementation plan, never a conversation about procedure
            (Akien, 2026-11-02). The sieves stay deterministic and never weigh a
            why; the LLM check comes only after a failure. It is never a lock pick
            because it has no third outcome: the ticket changes, or the sieve is
            fixed through its own ticket and proof. Nothing passes a ticket over a
            red; testing a sieve is what the ticket that fixes it does. (Q#62,
            Akien 2026-11-02.)
    19.14.8 A sieve's rule follows the ticket's kind (Akien, 2026-10-31: "for
            new/changed code tickets the rule is x, for fixit tickets the rule is
            y"). It is read off the ticket, so it stays deterministic, and 19.14.7
            is left for what x and y do not cover.
      19.14.8.1 x, new or changed code (code-seam): at BUILDME the named proof
                exists and its PROVES names the ticket, and it may be red, since a
                new proof is red before its build. At PROVED it is sealed green and
                hollow-measured.
      19.14.8.2 y, fixit (bug): at BUILDME the ticket names the red it fixes (the
                proof), and that proof really is red on disk now; the named proof
                may be red, fixing it is the job. The fix may change the test case
                itself without a ruling: the proof's why names the ticket and says
                what it tests and why it changed, and names any tooth it removed.
                At PROVED it is sealed green and hollow-measured, as x.
      19.14.8.3 A ticket cannot call itself a fixit to get y: y needs a real red on
                disk, which code checks. The harbor's proven-space rule (10.8) and
                the tester's rung 4 (11) each apply x or y by the ticket's kind;
                rung 4 no longer asks who answered.
