1 THE RUNGS (the complexity axis)
  1.1 PURPOSE: Name what every component is, so it has one place to live.
  1.2 INTENTION:
    1.2.1 Tool: a complete primitive. Has users, not an owner. Lives in cairn/tools/.
          Its data for a holder lives under that holder:
          ~/.cairn/devices/<device>/<instance>/tools/<tool>/
    1.2.2 Machine: tools plus the glue that holds them together. Has an owner. Lives
          inside its device (cairn/devices/<device>/machines/<machine>/), or in
          cairn/machines/ if several devices hold one.
    1.2.3 Device: its own process, in the rack, on the bus. See 2.
    1.2.4 Instance: every device has at least one; a singleton is 0.
    1.2.5 First class object (not a device): a thing with a charter that is not a
          rung of its own (Rescue, Graph Trees, Ticket).
    1.2.6 [Q#1: Test from the charters: "a thing that holds state is a machine, not a
          tool" (verdict machine, 2026-08). Is that still the line between 1.2.1 and
          1.2.2, or is it "has glue / has several tools"?]

2 DEVICE (Implemented as BaseDevice, part of the base tool; a first class object)
  2.1 PURPOSE: A device is a top level cairn entity.
  2.2 INTENTION:
    2.2.1 HARD BOUNDARY: TO ENCAPSULATE EVERYTHING ABOUT A DEVICE IN ITSELF.
    2.2.2 An internal device is its own process. External devices depend on
          implementation.
      2.2.2.1 A device may also own other processes besides its own. They are inside
              the device's boundary. Eg Cairn owns the bus process (where the shims
              run) and the ground loop.
    2.2.3 Devices are all peers with different jobs. See Operator (8).
    2.2.4 A device lives in its own folder in cairn/devices/<device>
    2.2.5 A device's data lives in ~/.cairn/devices/<device>/<instance>/
      2.2.5.1 The instance folder is a number, eg ~/.cairn/devices/cc/0/. A
              singleton is 0.
      2.2.5.2 A device may be a singleton or not, but nothing in its code differs by
              instance.
      2.2.5.3 A bare device name addresses instance 0 (`cc` means `cc 0`); the number
              is written only when it isn't 0. So instance 0 is the default: eg when
              one CC is the orchestrator, it's cc 0 unless directed otherwise.
    2.2.6 A device owns its state: only the device writes under its own
          ~/.cairn/devices/<device>/<instance>/ tree.
    2.2.7 A device holds machines and uses tools (from cairn/tools/). A tool's data
          for that device lives under the device:
          ~/.cairn/devices/<device>/<instance>/tools/<tool>/
    2.2.8 A device talks to other devices only over the bus, never by importing them.
      2.2.8.1 The bus is the only door, with exceptions (Akien 2026-10-22). Each
              is a client tool the device publishes:
        2.2.8.1.1 Database: because faster (13.2.5).
        2.2.8.1.2 Librarian: the embedding links will, I think, work better without
                  device boundaries. Talked about during the first pass at memory;
                  the words came later (4.5.2).
        2.2.8.1.3 Trouble: it has to be able to report when nothing else can, so
                  direct lines to trouble make sense for recovery reasons (7.3.4).
    2.2.9 Every device has the panes defined by base device (19.1.2.5.1): status,
          controls, chat, feed. The web server draws them (18).
  2.3 WHY: Because without hard boundaries Claude creates a tangled mess that exceeds
      Claude's own complexity limit far in advance of completion.
  2.4 COMMANDS:
    2.4.1 get - return a json of some requested thing
    2.4.2 help - the verb list with help strings; always human readable
    2.4.3 list - enumerates verbs, views and panes, any list of things that might be
          published; returns json (show list <foo> formats it for humans)
    2.4.4 put - is given mail or other future push things
    2.4.5 set <setting> <value> - change one of this device's settings (if any); see
          them with list settings
    2.4.6 send <to whom> <what> - this device sends mail to another device, eg
          cairn operator send librarian research <topic>
    2.4.7 show - same as get or list but formatted for humans
    2.4.8 start - start the device
    2.4.9 stop - stop the device
    2.4.10 A machine the device owns that has settings is reached through its device,
           with the same help/list/show/get/set: cairn <device> <machine> <command>
           (eg cairn cairn scheduler list). The bus only ever sees the device, which
           passes the rest down. Machines with no settings (eg base) don't need this.
    2.4.11 [Q#2: A device's own verbs beyond these (eg tester's run, librarian's ask):
           are they always reached as `cairn <device> <verb>`, and does `help` list
           them beside the common ones?]

3 TICKET (Abstract class - not a device, but a first class object; abstract)
  3.1 PURPOSE: A unit of work or attention, written down so it can be followed.
  3.2 INTENTION:
    3.2.1 TICKET is abstract. Every real ticket is one of the kinds below.
    3.2.2 The abstract ticket owns what every kind shares: its birth (cast), its plan
          file and its trail (the log beside it).
    3.2.3 [Q#3: Today tickets live in CairnCommons/tickets/ and their workflow gates
          are housed in harbor_master (5.9). Is the abstract Ticket a tool (code in
          cairn/tools/ticket/, data wherever each kind says), with harbor_master
          only reporting over it?]
  3.3 KINDS:
    3.3.1 Coding Ticket: what we usually mean.
      3.3.1.1 Has its own workflow stamped on it (the state string, with the cursor).
      3.3.1.2 Each workflow step declares what it needs.
      3.3.1.3 Carries its WATCHME spec.
      3.3.1.4 Lives in CairnCommons/tickets/ while staged; its trail migrates beside
              its code as that component's history while under way, and back to the
              commons after (Law 5).
      3.3.1.5 The ticket owns its refusals: a gate refuses a crossing on the ticket's
              behalf (ruling 2026-08-10). The gates are housed in harbor_master.
    3.3.2 Inference Ticket: the record of one call to the inference proxy, everything
          that happened to that request.
      3.3.2.1 The call runs the request against our graph trees first. If they can't
              answer, it asks the cloud "what nodes do I need to understand this?",
              integrates them, and runs the query against the trees again.
      3.3.2.2 When it asks an upstream LLM, the nest and its sieves sort out the
              lowest cost way to resolve it (eg by the request's domain), and the
              call is made the way the current constraint set says is best.
      3.3.2.3 Models can be specified, but shouldn't be most of the time. The graph
              trees can be bypassed, but shouldn't be most of the time.
      3.3.2.4 The call returns two pieces: the resolution of the request, and the
              inference ticket.
      3.3.2.5 Used for learning, or for debugging when something fails. A logging
              artifact, so disposable after 30 days.
      3.3.2.6 Inference tickets are transient: they live in the transient tree
              (4.3.2). (Q#4, Akien 2026-10-27)
    3.3.3 Trouble Ticket: an error that needs a non-automated fixer (CC or Akien).
      3.3.3.1 The intention for a trouble ticket is that it is a diagnostic report.
              EXACTLY like the Trouble Tickets in the Number Five Crossbar Telephone
              Switch. It MUST include EVERYTHING needed to diagnose, isolate, and
              repair the trouble.
      3.3.3.2 In the event a second trouble is observed while the first is open, a
              new ticket is NEVER issued, we just increment a counter on the ticket.
        3.3.3.2.1 A trouble has a point of origin, and that is how we match them up.
                  When raised with a condition, its emission source AND error message
                  are checked against open tickets. If found, increment the counter;
                  either way, pass the ticket back to the caller.
        3.3.3.2.2 The incrementing is part of the trouble ticket class.
        3.3.3.2.3 So the error a raiser reports is the same words every time it
                  happens; whatever changes from one time to the next (a pid, a
                  timestamp, a temp path) goes in the details, not the error.
      3.3.3.3 Trouble Tickets are disposable artifacts once closed. They are file
              artifacts, live in the logging tree, and are cleared out on a 30 day
              cycle by the cairn device during a sleep cycle.
      3.3.3.4 If a device experiences an error while servicing a request for another
              device, it can return a pointer to the trouble ticket, and the receiver
              can add new details if they wish.
      3.3.3.5 The test before raising one: can only CC or Akien fix this? If not, it
              is a log line, not a trouble. One problem, one trouble.
      3.3.3.6 They show on the operator's to-do list (8.2.6).
      3.3.3.7 Trouble tickets live inside the recovery device (7.3.4), since
              recovery has to work when other things don't.
      3.3.3.8 A trouble ticket is a work order to fix something. Whoever fixed it
              reports the fix to the originator (the device or machine that raised
              it), and the originator marks it fixed. A trouble that comes back is
              not designed for yet: if we start running into recurrent problems,
              we'll explore that. (Q#5, Akien 2026-10-27; "maybe" on who clears)
    3.3.4 Task Ticket: work the system needs done that does not change code, eg
          deploying our environment onto a second computer to use its compute.
      3.3.4.1 Every ticket has a workflow, even if it is just open/close; that is the
              nature of a ticket (an inference ticket too). A task ticket gets gates
              only if we ever see one closed without actually being done: that is
              what gates are for. (Q#6, Akien 2026-10-27)
    3.3.5 Ideas and questions are not tickets. An idea is a note that leads to an
          intention, and stops mattering once the intention is set down. A question
          exists only to deduce the why: once it is answered, what matters is the
          answer and the why, and nothing else. (Q#7, Akien 2026-10-27)

4 GRAPH TREES MEMORY SERVICE (not a device, but a first class object)
  4.1 PURPOSE: Where Cairn keeps what it knows, and what it holds for a little while.
  4.2 WHY: So everything the system learns is one connected body the librarian can
      see whole, and patterns can be exported from all of it. And so no device
      invents its own way of storing things: there are two ways, and every device
      uses them.
  4.3 INTENTION:
    4.3.1 Knowledge: one list of nodes, owned by the librarian.
      4.3.1.1 Other devices (codemother, chart, ...) keep no node tables of their
              own. They put what they learn into the librarian's nodes through the
              librarian's verbs on the bus.
      4.3.1.2 Each depositor gets its own index over the shared nodes, because each
              asked different questions first while assimilating the data.
      4.3.1.3 The librarian becomes aware of what other parts of the system learned,
              because it is all in its own store, so it can surface what others would
              find useful.
      4.3.1.4 Nodes are kept. The librarian can hand out the next free node.
    4.3.2 Transient: the transient tree (what the logging tree becomes).
      4.3.2.1 Everything held for seconds to days lives here: mail, logs, test runs,
              trouble tickets, inference tickets.
      4.3.2.2 Each kind of thing declares its lifetime, and it ages out on that clock.
      4.3.2.3 [Q#8: Who owns the transient tree? Draft: the Cairn device (it already
              owns clearing it in sleep, 5.2.1.4). And is it files on disk (as
              troubles are today, under ~/.cairn/logs/) or rows in the database?]
    4.3.3 A device's own state lives in its ~/.cairn/devices/<device>/<instance>/
          tree.
    4.3.4 Shareable provenance (charters, tickets, validations) is git JSON beside
          the code, never a row.
  4.4 ANTI-INTENTION:
    4.4.1 Each device growing its own pool of tables (today: 16 node tables, several
          owners).
    4.4.2 Any device reaching into the librarian's code other than through the trees
          tool it publishes (today chart does).
  4.5 COMMANDS:
    4.5.1 The librarian's verbs for depositing and walking. See 9.4.
    4.5.2 Walks go through the librarian's published trees tool, not the bus
          (2.2.8.1.2).

5 CAIRN DEVICE (cairn/devices/cairn/)
  5.1 PURPOSE: Represents the cairn system in aggregate
    5.1.1 Cairn owns everything about the system that is Cairn and hasn't been
          delegated elsewhere. A delegated domain belongs to its device, not to
          Cairn, even though it is of Cairn: eg the librarian is delegated learning,
          research and answering queries on what's learned; the embeddings device is
          delegated producing the embeddings we search with. The OS and hardware
          belong to Recovery (7.6).
    5.1.2 [Q#9: "the embeddings device" — there is no such device today; embeddings go
          through the inference proxy's embed verb. A device of its own to come?]
  5.2 INTENTION:
    5.2.1 Drive sleep process for devices
      5.2.1.1 Cairn keeps a list of scheduled things (the scheduler, 5.8). Each
              ground loop pulse, its shim has Cairn check that list against the
              clock: no match (eg 2245), the pulse is dropped; a match (eg 2300) is a
              PROBE, and it kicks off that thing in the Cairn device.
      5.2.1.2 Sleep is one of those scheduled things. At its time Cairn kicks off
              sleep by running its own sleep routine, then hands the sleep token over
              the bus to the next device, and so on. The rack's order is the token's
              order.
      5.2.1.3 What each device does in its sleep depends on the device: the librarian
              consolidates memory; the learning blocks do the same on their smaller
              memory sets; Recovery might run backups or SSD checks; some (eg the word
              graph embeddings device) do nothing.
      5.2.1.4 Cairn's own sleep has a lot to do, including clearing the logging tree
              of things older than 30 days.
      5.2.1.5 [Q#10: Earlier (2026-08-06) sleep's trigger was idle, "3 hours without a
              human", not an hour of the day. Now it's a clock entry (2300). Is it
              the clock now, or both (at 2300, if no human for N hours)?]
      5.2.1.6 [Q#11: "Away windows" (you tell Cairn you'll be gone x to y) were ruled to
              the cairn device 2026-09-30. Are they entries on the same scheduled
              list? What does Cairn do differently while you're away?]
    5.2.2 Own foundational components (bus, ground loop, rack, shims, scheduler,
          launcher, harbor_master).
    5.2.3 Owns the cairn command line launcher (5.3).
    5.2.4 Owns the transient tree and its 30 day sweep (4.3.2). [see Q 4.3.2.3]
    5.2.5 `cairn start` (= cairn cairn start) brings the system up: ground loop, bus,
          shims. `cairn stop` takes it down.
      5.2.5.1 Any cairn command brings up whatever it needs, including the whole
              install on the very first run (7.3.2). A well designed tool should
              disappear in use.
  5.3 launcher (machine)
    5.3.1 PURPOSE: The operator's ramp onto the bus.
    5.3.2 INTENTION:
      5.3.2.1 The launcher is a machine owned by the Cairn device. It is mostly a
              router.
      5.3.2.2 cairn <command>: first look for <command> in cairn/bin; if it isn't
              there, resolve it on the bus.
      5.3.2.3 The scripts in cairn/bin are the shortcuts. The folder IS the list: add
              a file to add one, delete it to remove one. A script may wrap a bus
              call (eg `cairn superclaude` → `cairn cc superclaude`; `cairn show
              temp` → `cairn recovery show temp`, added while we're chasing a heat
              problem) or do work itself (eg initialization, install).
      5.3.2.4 Scripts are Python wherever possible, run by Cairn's own interpreter,
              so one file works on every platform. Platform-specific ones match their
              platform: executable or .sh on Linux; .bat, .cmd or .ps1 on Windows.
      5.3.2.5 If a shortcut has the same name as a device, the launcher warns "x
              hides y" and then runs x.
      5.3.2.6 `cairn` speaks as the Operator (8).
      5.3.2.7 If Cairn isn't set up, or won't come up, the launcher calls the
              recovery device directly, not over the bus (7.3.1).
    5.3.3 HISTORY: today it is bin/cairn dispatching to bin/cmd/<name>, 31 commands,
          most of which do the work themselves. Where each goes: 5.10.
    5.3.4 [Q#12: cairn/bin (inside the package) or bin/ at the repo root (where it is
          now)?]
  5.4 bus (machine)
    5.4.1 PURPOSE: To provide an inspectable message passing system.
    5.4.2 INTENTION:
      5.4.2.1 It is the only way devices talk to one another.
      5.4.2.2 The shims all run in the same process with the bus.
      5.4.2.3 The bus handles two kinds of requests:
        5.4.2.3.1 Send - Asynchronous. Like sending an email.
        5.4.2.3.2 Show/Get - Synchronous. Like requesting a web page.
      5.4.2.4 The messages are stored in a SMALL buffer in memory. The bus keeps no
              database. A shim that needs to hold mail puts it in the transient tree
              (see Graph trees).
      5.4.2.5 The shims, in the same process with the bus, pick up the messages and
              route them to their device in whatever manner is appropriate.
      5.4.2.6 The Operator Device and the 'cairn' command are the operator's route
              onto the bus.
      5.4.2.7 The bus makes this messaging inspectable, the messages show on the
              bus' web panel as a "Murderbot Diaries" "Public Feed" the operator can
              review for purposes such as diagnostics.
        5.4.2.7.1 The feed is for debugging: "did the thing go by when I typed the
                  command?"
        5.4.2.7.2 It holds about the last 5 minutes, in the bus's memory buffer, and
                  is empty after a bus restart. The Cairn device owns it, since the
                  bus is its machine.
        5.4.2.7.3 The panel is drawn by the public_feed tool (19.3).
        5.4.2.7.4 Each line: from, to, time, sync/async, message.
      5.4.2.8 One bus per cairn instance (not per host). The bus owns cross system
              communication: extending the bus services to other host systems so
              we can run multiple heavy tasks at once.
      5.4.2.9 [Q#13: A sync request to a device whose shim must wake it: how long does
              the caller wait before it gets "not now" back? (V1 had 600 s then a
              trouble, before the wake moved to the shim, 5.7.3.2.2.)]
    5.4.3 HISTORY: the bus once wrote its ring to the database on each pulse
          (2026-09-06). V1's "keeps no database" replaces that.
    5.4.4 TOOLS: base, public_feed
    5.4.5 VERBS: None
  5.5 ground_loop (machine): the heartbeat
    5.5.1 PURPOSE: Cairn system daemon
    5.5.2 ANTI-INTENTION:
      5.5.2.1 What it must never grow back: a bus, a shim, probes, other kinds of
              pulses, staleness
    5.5.3 INTENTION:
      5.5.3.1 It is the only daemon in the system
        5.5.3.1.1 [Q#14: The bus process and the device processes also stay up. I read
                  "daemon" here as "the only thing that wakes on a clock"; everything
                  else wakes on an event. Right?]
      5.5.3.2 It re-starts itself when its own files change, unless
              COMMAND_DO_NOT_RESTART is set. COMMAND_EXIT stops it with exit code 0.
      5.5.3.3 A second copy refuses to start.
      5.5.3.4 it launches a script in each device's cairn/devices/<device>/groundloop
              called pulse.py, each as its own process.
      5.5.3.5 It writes one JSON record at the end of a pass with a list of each
              device: beat time, found device (folder), NOT FOUND or name, file
              mtime, pid it spawned. It does no checks and no takeover.
      5.5.3.6 [Q#15: Beat interval: 60 s today. Fixed, or a setting?]
    5.5.4 HISTORY: I once made daemons for everything and couldn't shut them down. So
          there is one loop, kept as simple as possible. In your words: "this is
          ENTIERLY an event driven system EXCEPT: Akien can say he'll be away from x
          to y times. and sleep."
    5.5.5 TOOLS: base
    5.5.6 VERBS: None
  5.6 rack (machine)
    5.6.1 PURPOSE: The place that holds the devices: a stack of rackmount devices,
          with the bus connecting them all.
    5.6.2 INTENTION: Just a dict with the device instances in it, in the form of
          their shims.
      5.6.2.1 It holds instances, not classes: one shim per instance. If we have cc 0
              and cc 1, two shims are running.
      5.6.2.2 It is the shims connected to the bus: who's in the rack is who's
              connected, which the bus can measure (agreed 2026-10-26, since each
              shim is its own process, 5.7.3.1).
        5.6.2.2.1 [Q#16: A shim that isn't running isn't connected, so it isn't in the
                  rack. Then pulse.py (5.7.3.4.1) can't learn its instances from the
                  rack; it needs the declared list (5.6.2.4). Right?]
      5.6.2.3 [Q#17: The sleep token goes in "the rack's order" (5.2.1.2). What is that
              order: alphabetical, order added, or declared?]
      5.6.2.4 [Q#18: Where are instances declared, so the rack knows to build cc 1? Draft:
              the existence of cairn/devices/<device>/<instance>/ in class-space
              (CLAUDE.md: one address in two roots).]
    5.6.3 HISTORY: today there is also a rack TOOL (19.20) that lists device folders.
          The machine holds running instances; the folder list may stay a tool.
  5.7 shims
    5.7.1 PURPOSE: Integrates its device into the system.
    5.7.2 WHY: So any program, ours or not, can live in Cairn as a device.
    5.7.3 INTENTION:
      5.7.3.1 Every device has a shim. Each shim is its own process, one per
              instance, and connects to the bus as a client (agreed 2026-10-26).
        5.7.3.1.1 WHY: in the bus process, updating one shim meant bringing the
                  whole bus down, and one shim's stall (or lock) was everyone's
                  (bug c2036433beaf: two shims' locks deadlocked in the bus).
                  Separate, a shim restarts itself when its own files change, like
                  the ground loop (5.5.3.2), and the bus stays up.
      5.7.3.2 The shim always starts its device. Nothing else does.
        5.7.3.2.1 It wakes the device when it's not running and is needed.
        5.7.3.2.2 If the device won't come up, the shim retries; after many retries
                  it files a trouble ticket for Akien and CC to check. This holds for
                  every wake: a request, a pulse, the sleep token (eg the web server
                  failing to come up).
        5.7.3.2.3 It answers what it can itself; when it can't (eg a health question
                  it holds no answer to), it wakes the device and asks.
        5.7.3.2.4 [Q#19: Does the shim ever stop its device when idle (eg the librarian
                  after N minutes unused), or only on `stop`?]
      5.7.3.3 Processes all messages from the bus for its device.
      5.7.3.4 pulse.py is part of the shim. The ground loop calling it tells the shim
              the pulse has arrived, and starts the shim if it isn't running.
        5.7.3.4.1 The ground loop finds one pulse.py per device. pulse.py reads its
                  own device's instances from the rack and pulses each one, so the
                  ground loop never needs to know instances exist.
        5.7.3.4.2 Any device's shim (through its pulse.py) can bring the bus up if
                  it's down: whatever is called brings up what it needs (5.2.5.1).
        5.7.3.4.3 pulse.py asks nobody anything. It starts the shim if it's down,
                  else tells the mechanisms inside the shim that need a pulse "here
                  ya go!" Only daemon-shaped things hang there, things that actually
                  need a heartbeat; everything else fires on events. Eg cc's Gmail
                  fetch, which IS messaging (12.3.6).
          5.7.3.4.3.1 WHY (Akien, 2026-10-26): "you were shoving more and more
                      things into the ground loop. making it slower and slower. the
                      point behind the ground loop firing pulse.py was to give you a
                      structure to hang deamons from, not managers."
      5.7.3.5 Processes the sleep cycle, if its device needs one: when the sleep token
              arrives, it wakes its device to do its sleep (the device does the
              sleeping, not the shim), then passes the token on. If its device won't
              come up, the shim files the trouble and still passes the token on, so
              the rest of the rack sleeps.
      5.7.3.6 Writes its runtime data, if any, to ~/.cairn/devices/<device>/<instance>/
      5.7.3.7 Three kinds of device sit behind a shim:
        5.7.3.7.1 Internal (eg librarian): ours, engineered to work with its shim, so
                  the shim adapts little.
        5.7.3.7.2 External (eg Claude Code): a program we don't control; the shim does
                  the adapting that lets it exist here.
        5.7.3.7.3 Virtual: the shim is the whole device. Eg a calibre device that
                  talks to calibre's own database, or a weather device over the
                  acurite data, for when something else in Cairn (say, a personal

7 RECOVERY DEVICE (cairn/devices/recovery/; Recovery And Installation Manager;
  holds the host (was the System device), install, upgrades, root, Rescue and
  trouble tickets)
  7.1 PURPOSE: Owns the host Cairn runs on. Gets Cairn installed and running, gets
      it running again when it breaks, and reports usefully when things don't work.
  7.2 WHY:
    7.2.1 A well designed tool should disappear in use: so little friction it's
          almost an extension of the user. Traditional software makes installing,
          opening and using it three separate tasks; Cairn makes them one command.
    7.2.2 It's part of our recovery system, so it has to work when other things
          don't, so I can report usefully on them.
  7.3 INTENTION:
    7.3.1 It operates when the bus is down, and when nothing is installed at all.
          The cairn command calls it directly.
    7.3.2 The very first run:
      7.3.2.1 A user downloads Cairn for the very first time. The readme says
              `cairn/bin/cairn librarian` (the full path, because no paths to the
              cairn command are set up). No database is installed. Nothing.
      7.3.2.2 The cairn command sees that, and calls the recovery device directly,
              reporting that we're not set up.
      7.3.2.3 It explains to the user that before we can start the librarian we need
              to do a few things first. Easy setup or DIY setup? Most people will
              take the easy setup.
      7.3.2.4 It asks for your password so it can install a, b, c, d. The password
              is kept only in an env var, and goes away when the program ends.
      7.3.2.5 If we can sort our location, we don't ask the user. If Cairn needs a
              password of its own (highly likely at some point), it asks during this
              setup.
      7.3.2.6 We install and set up everything, and the user is presented with a web
              based chat window (the librarian's).
      7.3.2.7 So the user entered a single command, and all needed setup was complete
              with an absolute minimum of interaction.
    7.3.3 Later the user changes something and breaks it. Recovery is called again,
          and invokes Claude (Rescue, 7.5) if needed to get it all fixed up.
    7.3.4 Trouble tickets (3.3.3) live here. Any device has a direct line to raise
          one, not over the bus (2.2.8.1.3).
    7.3.5 Install and upgrades live here. If xyz library needs an update, this is
          the component that does it. Any change to what the host is goes through
          here (7.6.2.1.1). The installer machine (today cairn/machines/installer)
          walks the host-seam intentions, verifies each, offers what's missing,
          applies, re-verifies.
    7.3.6 It has a shim, like every device, so it's on the bus when the bus is up
          (upgrades, its troubles, its last repair). It's still called directly
          when the bus is down or Cairn isn't installed (7.3.1).
    7.3.7 The setup panels (easy and DIY alike):
      7.3.7.1 Each panel is a block of text asking a question, with the default
              answer selected, so the user can go next, next, next until they reach
              the thing they want to change.
      7.3.7.2 A panel isn't one question each: a set of simple, related questions
              (eg 10) goes on one panel, to approve all or adjust before next.
      7.3.7.3 Or a statement: "the following necessary things will be installed:"
              and the list, with the why for each one.
    7.3.9 sudo_relay (machine; today its own device, cairn/devices/sudo_relay):
          Recovery's way to root on Linux, needed for installs and upgrades.
      7.3.9.1 A command goes in, runs as root, and a permanent audit record comes
              out: the command line, return code, stdout, stderr, plus an id and
              date. The audit folder keeps a rolling one month.
      7.3.9.2 A machine, not a tool: it keeps the audit records (state it must gate),
              and runs as its own root process inside Recovery's boundary (2.2.2.1).
      7.3.9.3 Other platforms get their own way to root (eg on Windows, Rescue and
              the installer run from an elevated PowerShell, 7.5.3.3).
      7.3.9.4 [Q#23: May other devices ask Recovery to run something as root (eg CC
              today uses it for ops), or is root only for install, upgrade and
              repair?]
  7.4 COMMANDS:
    7.4.1 cairn recovery: run setup, upgrade or repair by hand.
    7.4.2 cairn rescueclaude (7.5.4.1).
    7.4.3 cairn trouble live | clear (the trouble tickets, 7.3.4).
    7.4.4 cairn recovery sudo <command>: run one command as root through the relay

  7.5 Rescue (Claude Code outside Cairn; part of recovery, not a device of its own)
    7.5.1 PURPOSE: The mechanic. Claude Code running outside the system, called when
          Cairn won't run or isn't set up yet: "help, it's broken, come pick up the
          pieces or get us set up."
    7.5.2 WHY: A broken system can't fix itself, and a deterministic installer can't
          handle what it didn't foresee. CC is a senior builder INSIDE Cairn; Rescue
          is Claude outside it, getting it running and keeping it running.
    7.5.3 INTENTION:
      7.5.3.1 Each platform gets a good deterministic installer. When it fails, it
              falls over to Rescue.
      7.5.3.2 When something won't start (eg the database), Rescue is who gets
              called.

              (eg Windows, built from inside an elevated PowerShell, because Claude

      7.5.3.4 Needs nothing of Cairn's to run: no bus, no tmux.
      7.5.3.5 Launched automatically by a failed install or start, with "read this"
              and a file saying what happened and what it wants to make happen. The
              operator can also launch it by hand.
      7.5.3.6 Always launched with dangerous permissions, so it CAN do what's needed.
      7.5.3.7 What Rescue fixes by hand, it turns into a step in that platform's
              deterministic installer, so next time the installer handles it alone.
              Each rescue makes the next one less likely: the system keeps learning.
      7.5.3.8 On a new platform (eg Windows) a simple cairn.bat comes first: at the
              start it takes only the rescueclaude option, launching Claude with 200K
              context and dangerous permissions.
